book-article-gen

用五個 AI 各司其職寫出一篇好文章

給一個主題（例如「AA 制」），這個系統會自動產出 N 個版本的長文章。每個版本有不同的角色視角、不同的智慧錨點、不同的敘事風格。背後不是一個 AI 在寫，是六個專業分工的 AI Agent 一起協作完成 — 從找熱點、挖卡點、產角色、選書，到主編規劃版面、寫手實際寫稿。寫完還可選用另兩個 Agent：一個用「錨／歪／動」三維度自動審查 AI 味並迭代修改，一個剪出社群短版貼文。

一句話：這個系統在做什麼

輸入

一個主題字串，例如：
「AA 制」
「同居前要不要簽協議」
「原生家庭傷害」

輸出

N 個版本的長文章（3000–5000 字），每版角色、智慧錨點、風格都不同。例如三版分別是：故事體 + 哲思體 + 典故體。

傳統做法是：給 AI 一個主題，叫它寫文章。問題是這樣寫出來的東西很平、千篇一律、缺少深度。

我們的做法是：把「寫一篇好文章」拆成編輯部裡會出現的六種角色，每個角色用一個 AI Agent 扮演，讓他們協作分工。

為什麼要六個 Agent，不是一個？

一個 AI 同時要當熱點觀察者、卡點思考者、角色塑造者、博覽群書者、規劃調度者、實際寫稿者，會發生什麼事？答案是：每件事都做到 70 分，沒有一件 90 分。

但如果讓六個 AI 各做一件事，每個 AI 只專注在自己的視角上，整體品質就會跳起來。這就像真實的編輯部：寫稿的人不負責找選題，找選題的人不負責採訪，採訪的人不負責編輯定稿，總編輯不親自寫每一篇。

核心隱喻：把你的腦袋拆成六個專家，他們在你腦袋裡開會。每個人發言時別人不打斷，總編輯整合所有人的意見、為每個版本下指令，然後交給寫手實際成稿。

為什麼把「規劃」跟「寫稿」拆成兩個 Agent？

這是這個系統最近一次的重要重構。一開始，總編輯既規劃 N 個版本的差異化、又親自連續寫出 N 篇文章 — 全部塞在同一個 conversation。看起來最直覺，但實際跑下來會出現一個明顯問題：

後幾版越寫越像前幾版。當 N = 12，寫第 10 版時，total context 裡同時躺著前 9 篇完整內文 + 4 個 agent 的原始輸出。LLM 的 attention 會被既有 context 拉走 — 開頭套路化、用字重複、舉的例子在繞圈、原本想要的「角色 / 書 / angle 對比鮮明」被稀釋成「都長差不多」。

解法是把「規劃」和「寫稿」徹底分離成兩個 agent：

  • 總編輯 = 規劃：開完編輯部會議後，為每一版產出一份完整的 dispatch JSON（角色 / 書 / 風格 / 字數 / 這版的獨特切入角度 / 要避開什麼）。他不寫任何一個字。
  • 寫手 = 執行：每篇文章交給一個獨立的 寫手 subagent。每個寫手都是全新 session — 只看到自己這篇的 dispatch JSON，看不到其他版本、看不到前面的對話、context 天然乾淨。

這個拆法解決了三件事：

  1. Context 不再污染：每篇寫手只專心寫自己這篇，沒有「我剛剛已經這樣開頭過了，這次要不一樣」的負擔 — 因為他根本不知道有「剛剛」。
  2. 總編輯的腦袋也乾淨了：他不再需要把 N 篇 3000 字內文背在 context 裡。即使 N = 20，他的 context 也只有 N 份 dispatch + N 份回收，可以專心做「差異化品管」這件事。
  3. 差異化變成顯式產物：以前「N 版要對比鮮明」只是 prompt 裡的訴求，模型做沒做得到沒人看得見。現在每版的 angle_hint 和 avoid 是寫在 dispatch JSON 裡的明文 — 總編輯派發之前自己會檢查「N 個 hint 是不是真的不一樣」，不通過就重排。
真實編輯部的類比：主編開完選題會後不會親自寫 12 篇稿。他會把每篇的角度、訪談對象、字數寫成派稿單，分給 12 個寫手各自去寫。寫手之間互不干擾 — 這才是專業編輯部的工作流。

事後審查：用「錨／歪／動」打掉 AI 味（選用）

寫手寫出來的初稿即使結構對、角色立得起來、書引得到位，讀起來常常還是有一種「太工整、太順、太像文案」的味道。對仗句一句接一句、「○○感／○○性」滿天飛、所有事都發生在「某個午後」。這就是 AI 味。

我們的做法是接一個現成的審查工具：ai-free-editor（從社群作者那邊拿來的 skill）。它的設計哲學很乾淨：

  • 三個維度量 AI 味：錨（有沒有具體時間、地點、人名、感官細節）／歪（句子節奏對不對稱，AI 寫東西像被熨斗燙過）／動（用動詞推進還是用名詞鋪面）
  • 不整篇重寫：只標出最壞的 3 句、給改寫建議、一句話總結病灶。剩下的留給作者自己改
  • 事後審查，不事前約束：作者明確警告，把規則硬塞進寫作 prompt 會讓 AI 出現「假歪」（為了不對稱而刻意把句子斷得詭異，像裝口吃）跟「規避型僵化」（為避開禁用詞而用更彆扭的同義替換）。所以我們不去碰寫手的 prompt，只在事後接上審查
怎麼接：寫手寫完長文後，呼叫 mcp__editor__ai_free_review 工具。工具回報「【錨】1 分／【歪】2 分／【動】1 分」+ 標出 3 句最壞句子 + 改寫建議 + 一句話總結。寫手看完報告，自己改那 3 句、覆寫檔案。可跑 N 輪（config.toml 的 [review].iterations）。

為什麼是 MCP 工具，不是另一個 subagent？

本來這個審查流程設計上自然會想做成「寫手派發 審查 subagent」。但 Claude Agent SDK 有一條硬性架構限制：

The coordinator can only delegate to one level of agents; depth > 1 is ignored.

也就是 subagent 不能再派 subagent。寫手本身已經是 subagent，沒辦法再 fan-out 出一個審查 agent。為了讓寫手仍能保有「一版的完整 owner」這個身份（自己寫長文、自己審查改寫、自己出社群短文），審查跟社群短文這兩個流程就做成「in-process MCP tool」而不是 subagent：

  • 從 SDK 角度，呼叫 MCP tool 跟呼叫 Read／Write 沒兩樣 — 是「工具」而非「派 agent」，所以沒有層數限制
  • 工具的實作（agents/editor_tools.py）內部各自跑一個獨立的 query()，吃對應的 prompt（reviewer.md 或 social.md），回傳純文字結果
  • 工具的 query() 走的是跟外層 pipeline 同一條 SDK 認證路徑，所以不需要額外設 ANTHROPIC_API_KEY
  • 對寫手來說：呼叫 mcp__editor__ai_free_review(article, mode) → 拿審查報告 → 自己改 → Write。完全沒派 subagent，但行為跟「派審查 agent」一樣

同樣道理，社群短文也是工具：mcp__editor__social_rewrite(article, target_length, platform, original_style)。寫手拿到結果後自己 Write 到 _social.txt。

幾個刻意做的選擇：

  • Reviewer prompt 直接 copy 自原 skill，未改寫：原作者用「動詞推、不要對仗、不准飄詞」這種具體禁用清單調校過的東西，動了就破壞。任何「長文 vs 社群短文標準怎麼放寬」之類的差異，都由寫手在呼叫工具時透過參數告知（例如 mode="thread"），不去動 reviewer 本體
  • 寫手自己改，工具不重寫整篇：寫手知道這版的角色 voice、這版引的書、這版要對齊的 angle — 工具看不到這些。所以工具只回「審查報告」，寫手拿著報告自己改
  • 固定 N 輪、不看分數收斂：LLM 自評分數會 drift（越改越給自己高分）。固定 N 輪可預測、成本可控。1 輪就能打掉最明顯的 AI 味；3 輪以上會 diminishing return
  • 補錨不亂編：reviewer 如果發現缺錨會留下 【補錨：什麼時候？哪裡？跟誰？】 提示。寫手用 assigned_character 的既有設定合理填補，不憑空捏造真實人名地址
  • 預設關閉：審查會多花 N 輪 token，所以 [review].enabled = false 是預設。需要再開

六個 Agent 的分工

Agent 1
熱點 Agent
找入口：從主題拓展出讀者第一秒會停下來的關鍵詞與情感鉤子。未來會接 Thread / Dcard 爬蟲。
model: haiku
Agent 2
卡點 Agent
找問題：把表面議題挖到底層。讀者真正卡住的不是「該不該 AA」，而是「AA 在親密關係裡定義了什麼是『我們』」。
model: sonnet
Agent 3
角色 Agent
找人性：產出 5–7 個不同背景、立場差異大的角色。每個角色有自己的歷史、口吻、內在矛盾，讓總編輯挑來寫不同版本。
model: sonnet
Agent 4
書籍 Agent
找智慧：從本地書庫（目前 9 本，未來 500+）找出能回應卡點的書與段落。這是整個系統最難的一塊，下面會詳細展開。
model: opus
Agent 5
總編輯 Agent
找靈魂、做規劃：收齊前面四位的成果後，自己決定主軸、選 N 個對比強的角色、給每版指派一本書與一種敘事風格、為每版下一句獨特切入角度。他不寫稿 — 把派稿單交給寫手。
model: opus
Agent 6
寫手 Agent
執行成稿：每篇文章一個獨立寫手 session，N 個寫手平行跑。吃總編輯給的派稿單（角色 + 書 + 風格 + 字數 + angle）寫出長文；若派稿單帶有 review 欄位，自己呼叫審查工具跑 N 輪修改；若帶有 social_post，再呼叫社群工具並寫 _social.txt。一個寫手 = 一版的完整 owner。Context 天然隔離 — 寫第 12 版的人看不見第 11 版。
model: opus · N 個平行 instance
MCP 工具 7（事後·選用）
審查工具（mcp__editor__ai_free_review）
事後審查：用「錨／歪／動」三維度評分中文文字的 AI 味、標出最壞 3 句、給改寫建議、一句話總結病灶。不整篇重寫。寫手拿到報告後自己改那 3 句並覆寫檔案。可跑 N 輪。Prompt 來自社群作者的 ai-free-editor skill，直接複製、未改寫。不是 subagent（SDK 不允許 subagent 二層 dispatch），是 in-process MCP tool — 內部跑一個獨立 query()。透過 config.toml 開關。
model: sonnet · 預設關閉
MCP 工具 8（衍生·選用）
社群工具（mcp__editor__social_rewrite）
找鉤子：在每篇長文寫完後啟動，從原文剪出最有畫面/情緒/張力的故事片段當錨點，改寫成適合 Threads / IG / FB 的短版貼文。不是摘要，是把那顆鑽石單獨呈現。透過 config.toml 開關。
model: sonnet · 預設關閉

衍生：社群工具怎麼把長文剪成貼文

長文寫好之後，常常還想配一個社群版（Threads / IG / FB）。但是直接讓 AI 「把這篇 4000 字濃縮成 300 字」，產出來幾乎都很無聊 — 因為它在做摘要，不是做鉤子。

核心觀念：社群貼文的目的是鉤人，不是傳遞資訊。所以對的做法是 — 在原文裡找出最有畫面、最有情緒、最有張力的那個 micro-story，剪下來、磨亮、單獨呈現。讀者沒看過原文也讀得懂，且讀完想去看完整版。

必備 #1
人物

必備 #2
情緒
愣住、心一沉、突然懂了
必備 #3

時間、地點、感官細節
必備 #4
張力
A 以為 X，但 B 一句話戳穿

四種平台、四種口吻

平台節奏結尾
threads第一行直接進現場、一句一段、大量換行、口語留白 / 問句 / 沒答案
ig有氛圍感、段落稍長、可以有比喻一句 takeaway，不雞湯
fb段落正常、可以串多個 scene、最完整可點題或問問題引留言
general折衷留白

關鍵設計：書名整個拿掉

長文裡的書（《非暴力溝通》、樊登在解讀某書時說……）在社群版會被整個移除，那句智慧轉成第一人稱重述：

長文（直接引）

「樊登在解讀《非暴力溝通》時說：『我們的感受根源於我們自身的需要。』」

社群版（轉化）

「我朋友跟我講過一句話，我記到現在 — 你會生氣，從來不是因為對方做了什麼，是你某個需要沒被看見。」

原因：社群是「朋友式對話」的場域，引用書名會立刻出戲；硬塞書面引用節奏直接斷掉。

編輯 config.toml：

[social_post]
enabled = true

跑完輸出資料夾會多出 output_{i}_social.txt，與長文 output_{i}.txt 並排：

最難的問題：書籍 Agent 怎麼真的去「查書」

這是整個系統的核心難題，也是最值得花時間講清楚的部分。

問題長什麼樣

「書籍 Agent」要做的事聽起來很簡單：給定一個議題（例如「AA 在親密關係裡定義了什麼是『我們』」），從書庫裡找出能回應這個議題的書，並從書裡找出可以引用的具體段落。

但魔鬼在細節裡：

難題一：書太多，塞不進 AI 的腦袋

目前書庫有 9 本書、未來計劃擴到 500+ 本。500 本逐字稿總共 ~29MB，相當於 700 萬個 token。任何 AI 模型的「記憶容量」都裝不下 — 即使是目前最大的 1M token 模型也不夠。

難題二：抽象概念，搜尋不出來

議題是「AA 制」，但相關的書裡寫的可能是「共同體」「互依」「界線」。這些字面上完全不像，但思想上是同一回事。傳統的關鍵字搜尋抓不到這種對應。

如果書籍 Agent 沒做好，最常見的失敗就是：AI 開始瞎掰一本根本不在書庫裡的書。它會講「《XXX》這本書裡提到…」，但那本書其實只存在於它的記憶裡，不在我們的本地書庫。這在內容生產上是致命的 — 讀者想去找原書會找不到。

解法：兩層檢索（Two-Layer RAG）

我們的設計把「找書」拆成兩個截然不同的步驟，每一步用最適合它的技術：

為什麼一定要分兩層

層找的是用的技術為什麼
第一層
（概念）		 「思想對應」
哪本書在談這個議題的本質		 LLM 直接讀全部書的「目錄樹」
（精簡版 mindmap）		 抽象概念匹配是 LLM 的強項。「AA」要連到「共同體」需要推理，不是字面比對。
第二層
（段落）		 「可引用原文」
具體哪段話最能支撐論點		 向量搜尋
（bge-m3 + chromadb）		 具體文字匹配是向量的強項。資料量大（500 本 ~6 萬段）只能用向量過濾。

如果只用第一層 LLM 推理：模型很容易「想到對的方向，但編出不存在的原文」（也就是 hallucination）。

如果只用第二層向量搜尋：抓得到字面相關的段落，但抓不到抽象思想對應 — 因為「親密關係的共同體」跟「AA」字面差太遠。

兩層配合，才能既抓對方向，又拿到真實原文。

關鍵技巧：第一層只塞「精簡目錄樹」，不塞全文。每本書原本的逐字稿是 ~58KB，但目錄樹只有 ~1.5KB（標題 + 章節 + 重點概念）。500 本目錄樹加起來 750KB，相當於 19 萬 token，仍能完全塞進 1M context 的 Opus 模型一次讀完。

逐字稿則完全不進入 prompt — 它們躺在向量資料庫裡，第二層只取出 query 命中的段落（每次 ~15 段，~8K token）。

規模上限預估：≤ 500 本可單次塞入；500–1000 本需要再加一層「類別過濾」（先選類別再選書）；> 1000 本需要更精緻的多階段檢索。當前設計把 hooks 留好（每本書的 metadata 已經有 tags 欄位），未來擴充不需要改 pipeline。

目前的限制與下一步

  • 熱點 Agent 是 stub：目前只是把使用者輸入的主題往下傳。下一步接 Thread / Dcard 爬蟲，自動找熱貼、抓鉤子。
  • 書籍 hallucination 偶發：即使 prompt 嚴格寫了「只能引用本地書庫」，模型偶爾還是會把它記憶中的書混進來。需要在最後加一個 programmatic 驗證層 — 自動掃描輸出檔，把任何不在書庫裡的書名標出來。
  • 研究階段仍循序執行：熱點 → 卡點 → 角色 → 書籍 是依序的（後者依賴前者輸出）。書籍跟角色其實可以併行（都只依賴卡點），未來會優化。
  • 沒有自動評估：目前靠人工比對 example 樣本判斷品質。未來可以加一個「品質 agent」自動打分（開頭抓人度、卡點深度、引用真實性、字數合理性、N 版之間的差異化程度）。

關鍵設計抉擇

選擇為什麼
多 Agent，不是單一 prompt每個視角專注，總體品質高於混合單一 agent
用 Claude Agent SDK，不是自己 wrap APISDK 已經處理了 subagent dispatch、context 隔離、工具呼叫等基礎建設
第一層用 LLM 而非向量抽象思想對應 embedding 抓不到，必須讓 LLM 推理
第二層用向量而非 LLM具體文字匹配 + 大量資料 only embedding 撐得住
本地 bge-m3 而非雲端 embedding中文 SOTA、零成本、500 本一次性 index 30 分鐘
Opus 給總編輯與書籍，Sonnet 給其他總編輯與抽象書籍選擇需要強推理；其他工作 Sonnet 夠用，省成本
社群／審查做成 MCP 工具，不是 subagentSDK 不允許 subagent 二層 dispatch。改用 in-process MCP tool（內部各跑一個獨立 query()），讓寫手仍能「自己接管這版的完整流程」— 工具 vs subagent 對使用者體驗一樣，但繞過架構限制
社群工具寫一篇呼叫一篇，不批次每寫完一版立刻呼叫剪短，避免上下文遺失。批次處理會讓社群工具看不到原文細節
社群版主動移除書名社群是「朋友式對話」場域，書面引用會立刻出戲、節奏斷掉
審查者只回報告、不整篇重寫整篇重寫會丟失寫手手上的角色 voice / 書的引用方式。讓寫手拿著報告自己改那 3 句，保留 context
